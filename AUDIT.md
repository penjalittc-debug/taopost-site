# AUDIT.md — TaoPost (taopost.ru)

Дата аудита: 2026-08-03  
Фаза: **1 — только чтение**. Правки не вносились.  
Аудитор: единая продуктовая команда (маркетинг + PM + UX/UI + FE + BE + SEO + контент).

---

## 1. Резюме для руководителя

TaoPost — технически крепкий SSR-лендинг на Next.js 15 (App Router) с грамотной базой SEO: единый `<h1>`, уникальные `title`/`description`/`canonical` на каждой из ~65 страниц, sitemap.xml, robots.txt, Schema.org (Organization, Service, Product, BreadcrumbList, FAQPage, HowTo, Article), HSTS, X-Frame-Options, gzip, `next/image` с AVIF, Яндекс.Метрика с webvisor и трекингом целей. 20 SEO-страниц городов с уникальным `localText` и 5 маркетплейс-лендингов заводят «длинный хвост» — фундамент под трафик уже есть.

**Три главные проблемы:**

1. **Дубль домена `www.taopost.ru` → HTTP 200 без 301** ([app/page.tsx:19](app/page.tsx#L19) canonical проставлен, но nginx не редиректит www). Яндекс и Google уже могут делить сигналы между двумя зеркалами.
2. **Отсутствует юридическая база 152-ФЗ/GDPR-минимума:** нет cookie-уведомления, нет обязательного чекбокса согласия на обработку персональных данных в формах ([LeadForm.tsx:164-167](components/LeadForm.tsx#L164), [B2BForm.tsx](components/B2BForm.tsx)). Все отзывы — демо-заглушки на `/reviews/placeholder.svg` ([lib/reviews.ts:20-90](lib/reviews.ts#L20)); при обнаружении фейковых отзывов Google/Яндекс могут наложить санкции.
3. **Демо-статика отдаётся без кеша** (`Cache-Control: public, max-age=0` для `/logo.png`, `/warehouse/*.mp4`, `/certificate.jpg` и т.д. в public/), а объёмный делитель в калькуляторе (`VOL_DIVISOR=6000` в [Calculator.tsx:11](components/Calculator.tsx#L11)) **расходится** с формулой на странице тарифов («÷5000», [tarify/page.tsx:31](app/tarify/page.tsx#L31)). Клиент, сверивший цифры, потеряет доверие.

**Ожидаемый эффект от Волны 1 (быстрые победы)**: +5-15% индексируемых страниц (после устранения дубля www), −30-40% CLS-рисков от эффективного кеша статики, устранение юридического риска блокировки Роскомнадзором.

## 3. Разделы по ролям

### 3.1 Маркетинг и PM

**Позиционирование.** Первый экран говорит понятно: «Доставка и выкуп товаров из Китая — экономия до 60%». Лицензия КНР + собственный склад — сильные дифференциаторы, вынесены в pill и футер (лицензия). Три сегмента (Одежда/Кроссовки/Опт) — грамотная сегментация трафика прямо в hero.

**Конкурентный контекст (не проверено — требует внешнего сравнения с cdek-china.ru, chinacargo.ru, cargomsk.ru, kd-vlgd.ru, tenno.ru).** Из того, что есть внутри проекта: TaoPost делает ставку на «китайское юрлицо + собственный склад в Гуанчжоу» и «онлайн-кабинет `app.taopost.ru`» — оба сильные крючки против «серых» карго. Отсутствует раздел сравнения тарифов с конкурентами (кроме TgVsUs — сравнение с Telegram-байерами), это упущение для нижней воронки.

**ЦА и сценарии.** Продукт заявлен для физлиц + B2B. Три чипа в hero покрывают: одежда/электроника, кроссовки, опт. Отдельный лендинг `/business` для B2B. Однако нет отдельного пути «страховой случай/что делать если посылка потерялась» — только общий FAQ на `/garantii`.

**Воронка.** Основные CTA: Telegram (главный, во всех блоках), «Оформить в личном кабинете» (`app.taopost.ru`), «Рассчитать стоимость» (Calculator/LeadForm). Внутренняя форма ведёт на `/api/calculator` → Resend → email. Проблема: **три конкурирующих CTA** в hero (Telegram + ЛК + калькулятор) без явной иерархии — размывает конверсию. Плюс `TelegramFloat` + `StickyMobileCTA` на мобиле дублируют Telegram.

**Аналитика.**
- Yandex.Metrika ✓ (`ssr:true`, `webvisor:true`, `clickmap`, `ecommerce:"dataLayer"`, `trackLinks:true`, `accurateTrackBounce`). Инициализация корректная, с антидубликатной защитой ([app/layout.tsx:68-76](app/layout.tsx#L68)).
- **Google Analytics 4 — отсутствует.** Для приоритета «Яндекс» это ок, но при работе с Google рекомендую подключить GA4 (иначе поведенческие сигналы Google из GSC ограничены).
- Цели: реализованы через data-атрибуты `data-ym-goal` + один делегированный listener в `MetrikaTracker.tsx:59-73`. Отслеживаются: `telegram_click`, `cabinet_click`, `phone_click`, `email_click`, `channel_click`, `lead_form_submit`, `city_card_click`, `hero_segment_click`, `article_cta_*`, `exit_intent_open/close/reason`, `sticky_calc_click` и др. — **очень хорошая покрышка.**
- UTM-обработка автоматическая (Метрика забирает из URL), но **не сохраняется в лидах** — в письмо на email цели/UTM не пробрасываются ([api/calculator/route.ts:104-116](app/api/calculator/route.ts#L104)). Плохо для сквозной аналитики.
- Отслеживание отправки формы через `data-ym-goal="lead_form_submit"` + fallback `ymReachGoal` в JS ([LeadForm.tsx:31,150](components/LeadForm.tsx#L31)) — дублирование, потенциальная двойная фиксация цели. Проверить в отчёте по целям.
- **Отслеживания звонков (call-tracking) — нет.** Ни колл-трекинг сервис, ни виртуальные номера. `tel:` только шлёт goal `phone_click`, но не различает источники.

### 3.2 UX / UI

**Информационная архитектура.**
- Меню: О компании, Тарифы, Маркетплейсы (якорь), Для бизнеса, Гарантии, Блог, Контакты — 7 пунктов, глубина ≤ 2. Хорошо.
- Хлебные крошки есть на второстепенных страницах (breadcrumb JSON-LD + видимые). На главной естественно нет.
- Поиска по сайту нет (для лендинга не критично, но для 8+ статей и 20 городов — стоило бы иметь search-endpoint).

**Ключевые сценарии — трение.**
- Главная → LeadForm: 4 поля (город, телефон, транспорт-таб, вес-опционально) — минимум трения, ок.
- Главная → Telegram: везде. Возможно избыточно (Header + Sticky + Float + В каждой секции по кнопке — 15+ Telegram-точек в HTML).
- Мобильный → CTA-звонок: `tel:+79772767778` в hero и footer. Ок.
- Проверка заказа/трекинг: **отсутствует на сайте**, редирект на `app.taopost.ru`. Для клиента, который ищет «где моя посылка», это шаг наружу — стоило бы iframe/минимальный статус на сайте.

**Первый экран.** За 5 секунд считывается: услуга, ключевая выгода (−60%), сегменты, цена (от 350 ₽/кг), CTA. Достаточно.

**Формы.**
- `LeadForm` — 3 обязательных + 1 опционально. HTML5 autoComplete (`address-level2`, `tel`), inputMode='tel'/'decimal', обратная связь через `<p className="lf__err">`. Honeypot ✓ ([:14,136-144](components/LeadForm.tsx#L14)). После ошибки — fallback Telegram + телефон. Success-state отдельный. **Хорошо.**
- `B2BForm` — валидация мягкая (`company>1, phone>4, volume>0`), нет типа поля phone (тип text), нет чёткого сообщения об ошибке отдельных полей — состояние только `idle/sending/ok/error`. Улучшить.
- **Нет чекбокса «Согласен на обработку персональных данных»** — только текст «Нажимая кнопку, вы соглашаетесь с политикой». Юридически спорно (152-ФЗ рекомендует явное согласие для обработки без договора).
- Валидация: телефон в LeadForm проверяется на 10+ цифр клиентски (`canSend`), но не форматируется автоматически (нет маски).

**Визуал.** Единая дизайн-система (`.tp-*` утилиты + `styled-jsx`). Палитра: коралловый + тёмно-зелёный, кремовый фон. Типографика Rubik. Стиль современный, качественный. Отступы консистентны (через `section-pad`, `tp-section`).

**Доступность (WCAG 2.2 AA).**
- Контраст: основной текст `#0A0F1C` на белом ≈ 19:1 ✓; `#4B5563/#6B7280` ≈ 6-8:1 ✓; `#9CA3AF` на белом ≈ 3.4:1 — **на грани**, для мелкого текста в футере и `.lf__note` может не проходить AA (4.5:1).
- Фокус-состояния: у input есть `:focus` (border-color + box-shadow). У кнопок и ссылок кастомного focus-visible **не задано** — используется браузерный дефолт, что в некоторых темах даёт слабую видимость.
- Alt-тексты: у `logo.png`, `certificate.jpg`, `article.image` — есть, осмысленные ✓. У иконок lucide — SVG без alt (это ок для декоративных, но в StickyMobileCTA и других кнопках иконка + текст → в порядке).
- Семантика: `<main>`, `<header>`, `<footer>`, `<nav aria-label="breadcrumb">`, `<section id="...">` — расставлены. `role="tab"`/`aria-selected` на чипсах в hero ✓. `role="dialog"/aria-modal/aria-labelledby` в ExitIntent ✓.
- Клавиатурная навигация: Escape закрывает ExitIntent и zoom в Reviews ✓. Focus-trap внутри модалки ExitIntent **не реализован** (Tab может уйти за модалку).
- `prefers-reduced-motion`: `FadeIn.tsx:27` — **уважает** ✓; `ExitIntent.tsx:218-236` и `StickyMobileCTA.tsx:53-56` — **не учитывают** (keyframes+transition идут в любом режиме).

**Мобильная.**
- Тап-зоны: Sticky mobile CTA 44+px ✓, кнопки в форме 44+ ✓. Иконки в хедере 40px — ок.
- Гор. скролл: не обнаружен в CSS (`max-width: 100%`, `box-sizing: border-box`).
- Шрифты: `clamp(28px, 4vw, 44px)` для H2, `18px` для лида — читаемо.
- **Sticky mobile CTA нельзя закрыть** ([StickyMobileCTA.tsx:1-98](components/StickyMobileCTA.tsx)) — навсегда занимает нижнюю полоску экрана. При заполнении формы перекрывает поля.

### 3.3 Фронтенд

**Разметка.** Один `<h1>` на страницу ✓. Иерархия H2/H3/H4 корректная (`grep`: `1 h1, 16 h2, 25 h3` на главной). Семантические теги есть. `dangerouslySetInnerHTML` только для JSON-LD и HTML контента статей блога ([blog/[slug]/page.tsx:187](app/blog/[slug]/page.tsx#L187) — источник данных доверенный, TS-константы).

**CSS.**
- Методология: Tailwind v4 + BEM-подобные классы (`.tp-*`, `.hero3__*`, `.lf__*`) в `styled-jsx`. Компонентная изоляция.
- Много inline `style={{ ... }}` в SEO-страницах (blog, kontakty, o-kompanii, tarify) — это утяжеляет HTML (главная 279 KB, tarify 87 KB, taobao 123 KB) и мешает переиспользованию. Пример: [blog/page.tsx:37-186](app/blog/page.tsx#L37) — почти весь стиль инлайн.
- Дубли: цвета вынесены в `--green`, `--coral`, но hex-эквиваленты (`#005C43`, `#FF5A47`) также захардкожены во многих файлах.
- CSS-бандл `8448d36f5cabb9fc.css` — 30 KB несжатый / 5.3 KB gzip. Ок.

**JS.**
- Крупные чанки (несжатые): 287 KB, 183 KB, 110 KB, 82 KB (в `.next/static/chunks`) — суммарно 1.4 MB. С gzip уменьшается до ~400 KB. Приемлемо для лендинга такого масштаба, но 287 KB чанк стоит разбить.
- Preload: 2 woff2 (Rubik), 1 image srcset (logo w=48/96), 1 script (`fetchPriority="low"`). Настроено ✓.
- Скрипты сторонние: **только Yandex.Metrika** (`strategy="afterInteractive"` — не блокирует FCP). GA4/VK Pixel/Facebook/Mail.ru/Clarity — нет.
- Bundle-analyzer не подключен. Рекомендую добавить, чтобы отслеживать рост чанков.
- Ошибка/предупреждения консоли: не проверено автоматизировано, требует ручной проверки в браузере на всех ключевых страницах.

**Core Web Vitals.** Реальные метрики CrUX не проверены (нужен доступ к PSI/CrUX API). Оценка на основе кода:
- **LCP:** hero-h1 или карточка hero, скорее всего текст + inline SVG. Preload logo ✓. Шрифт `display: swap` ✓. Оценка: ≤ 2.5s на быстром соединении, риск на медленном mobile из-за большого HTML (279 KB).
- **INP:** взаимодействий немного, React-состояния в hero чипсах, калькуляторе, форме — легковесные. Ожидаемо ≤ 200ms.
- **CLS:** `next/image` с `fill` + `sizes` или `width/height` — везде задано. Единственный риск — Hero-визуал абсолютно позиционирован в контейнере фикс. высоты (480px на desktop, 440/420 mobile). Ок.
- **Проблема:** статика в `/public` без long-term cache (`Cache-Control: public, max-age=0` для `/logo.png`, `/warehouse/*.mp4`, `/certificate.jpg`, `/dragon.webp`). Все прямые обращения тянутся заново. Настроить nginx `expires 30d immutable` для `/public/*`.
- **Проблема:** видео `/warehouse/video-*.mp4` (467 KB и 1.3 MB) — отдаются без кеша. При каждом посещении браузер их подгружает заново (даже с ленивой загрузкой при попадании в вьюпорт).

**Изображения.**
- Форматы AVIF/WebP через `next/image` работают ✓ (Content-Type: image/avif при `Accept: image/avif`).
- В `/public/products/` часть в WebP/AVIF (`nike-air-force-1.webp`, `adidas-samba-og.avif`), часть в JPG до 124 KB (`levis-501.jpg`, `carhartt-wip-jacket.jpg`). Через `next/image` они пережимаются, но исходники крупные — можно оптимизировать offline.
- `/public/warehouse/photo-1.jpg` ... 5.jpg по 300-400 KB — большие исходники. Через `_next/image?url=...&w=1080` → AVIF 130 KB. Ок, но исходники стоит подрезать до 1600px.
- `/certificate.jpg` — 204 KB, 1200×883 JPEG. Использован в `next/image` с `sizes="(max-width: 768px) 100vw, 320px"` — оптимизируется.
- `alt` осмысленные, для декоративных иконок используются SVG без alt.

**Адаптивность.**
- Брейкпоинты в CSS: 480, 600, 640, 768, 880, 900, 960, 1024. Хаотично, но покрывает основные размеры.
- Проверить визуально на 360/768/1024/1440/1920 — требует ручной проверки в браузере.

**Анимации.** Только `transform` и `opacity` — не вызывают layout thrashing ✓. `will-change: transform` у кнопок ✓.

### 3.4 Бэкенд

**Архитектура.**
- Один API-роут `/api/calculator` — принимает и обычные заявки, и B2B (через флаг `b2b:true`). Разделение — функция `handleB2B` в том же файле. Простая, читаемая архитектура.
- Runtime: `nodejs` (Resend требует Node) ✓.

**API.**
- Валидация: телефон 10-15 цифр ([api/calculator/route.ts:36-39](app/api/calculator/route.ts#L36)), длина полей ограничена `.slice(0, N)`, JSON парсится в try/catch с 400. Категория, описание для B2B — ограничены 80/2000 символов. **Хорошо.**
- Ошибки: 400 (invalid JSON, missing fields, invalid phone), 429 (rate limit), 500 (missing API key), 502 (Resend error). Коды корректные.
- Honeypot: поле `website` при заполнении возвращает `{ok:true}` без отправки ([api/calculator/route.ts:65-67](app/api/calculator/route.ts#L65)) ✓.
- HTML-эскейпинг перед вставкой в email ✓ (`esc` функция).
- **Отсутствие CSRF-защиты**: origin/referer не проверяется. Для форм на публичном сайте это стандартно (и cookies не используются), но при подключении к внешнему источнику может понадобиться.

**Rate-limit.**
- In-memory `Map<string, number[]>`, 5 запросов/60сек на IP ([api/calculator/route.ts:10-33](app/api/calculator/route.ts#L10)).
- **Проблема:** при PM2 в cluster-режиме лимит работает per-worker (комментарий в коде это подтверждает). При 4 воркерах реальный лимит становится 20/мин.
- **Проверка на проде:** 7 запросов подряд с одного IP на `/api/calculator` — все вернули 400 (missing fields), 429 не сработал. Возможные причины: (а) все воркеры получили по 1 запросу; (б) IP из `x-forwarded-for` не парсится корректно за nginx; (в) rate-limit проверяется только для валидного JSON. Требует ручной проверки в PM2-логах.
- **Рекомендация:** вынести в Redis/Upstash при масштабировании, либо перенести rate-limit в nginx `limit_req_zone`.

**База данных.** Нет — лиды идут прямо в email. Плюс: минимум инфраструктуры. Минус: нет истории заявок, нет анти-фрода, нельзя переиграть отправку при сбое Resend.

**Производительность сервера.**
- Next.js SSR + агрессивный кеш: `cache-control: s-maxage=31536000` + `x-nextjs-cache: HIT` — прекрасно, страницы отдаются из кеша.
- TTFB (по замерам curl): ~200-400ms (Selectel, RU) — приемлемо.
- CDN: **не используется**. Для РФ-аудитории с ру-хостингом это ок, но для регионов (Владивосток, Хабаровск) добавит задержку.

**Безопасность.**
- HTTPS/HSTS: `strict-transport-security: max-age=31536000; includeSubDomains` ✓. Редирект http→https 301 ✓.
- Заголовки: `X-Frame-Options: SAMEORIGIN` ✓, `X-Content-Type-Options: nosniff` ✓, `Referrer-Policy: strict-origin-when-cross-origin` ✓, `Permissions-Policy` ✓.
- **Content-Security-Policy — отсутствует.** При наличии `dangerouslySetInnerHTML` (JSON-LD, HTML статей блога) стоит хотя бы установить `default-src 'self'; script-src 'self' 'unsafe-inline' mc.yandex.ru; ...`. Без CSP XSS в статьях блога (если в будущем контент станет пользовательским) — реальный вектор.
- Секреты: `.env.example` не найден. `RESEND_API_KEY`, `RESEND_FROM`, `RESEND_TO` берутся из env — правильно. Проверить что `.env`/`.env.local` в `.gitignore` ✓ (стандартный `.gitignore` от Next).

**Индексация и доступность.**
